# День 27 — Telegram и CLI с локальной моделью

Статус: **реализовано и проверено; фактические ответы и ограничения — в results/**.

## Требование и результат

Реальное приложение отправляет запросы локальной LLM и показывает ответы
без облачных моделей. Делаем Telegram-бота на ПК и полноценный CLI:
CLI закрывает обязательную проверку приложения независимо от доступности Telegram.
Во всех интерфейсах работает отдельная сущность `Agent` из `agent.py`,
собственная история сессии и прямой HTTP Chat API client без SDK.
Для автоматической проверки доступны CLI и JSONL stdio protocol.

## Что установлено исследованием

- Telegram credentials находятся в корневом `prod.env`, ключ `TG_BOT_TOKEN`.
- Read-only `getMe` подтвердил действующий `@producto_online_bot`.
- Polling и allowlist проверены по реальному входящему `/start`; бот отправил
  приветствие. Обычный live Telegram LLM-ответ отдельно не заявляется;
  полноценный диалог модели подтверждён CLI/JSONL.
- Пользователь согласовал размещение бота на ПК. VPS в дне 27 не требуется.

## Шаги

1. Скопировать проверенную основу дня 26, добиться независимого запуска.
2. Вынести диалог в отдельный `agent.py`: bounded role/content history, изоляция сессий,
   сброс, последовательность запросов внутри одной сессии.
3. CLI использует тот же service; выводит текст либо JSON с metadata.
4. Telegram реализовать обычными HTTP-вызовами Bot API, без agent frameworks:
   `/start`, `/reset`, обработка текста, понятные сообщения ошибок.
5. Long polling работает на ПК и не требует публичного webhook. До включения
   проверить `getWebhookInfo`; существующий webhook не удалять молча. При
   конфликте описать причину и согласовать переключение используемого бота.
6. Ограничить доступ allowlist Telegram user/chat IDs; не отвечать посторонним.
   User ID получаем из фактического входящего update; токен не печатаем.
7. Соблюдать Telegram length limits: отправлять длинный ответ частями,
   учитывать ошибки/429 Telegram отдельно от ошибок LLM. Не включать случайный
   parse mode, способный ломать код и citations.
8. Проверить bounded concurrency: один диалог не мешает другому, timeout
   не оставляет session lock навсегда. Секреты и полные Telegram updates
   не сохранять в общедоступные результаты.
9. Выполнить проверки CLI, затем проверить Telegram transport без исходящих
   сообщений посторонним. Реальный ответ бота демонстрируется при входящем
   тестовом сообщении пользователя; отсутствие такого сообщения явно отметить.

## Проверки вне Telegram

| Сценарий | Что подтверждает |
|---|---|
| «Меня зовут Алексей» → «Как меня зовут?» | История общей chat-цепочки |
| Вторая сессия: «Как меня зовут?» | Нет утечки имени из первой сессии |
| Сброс первой сессии → тот же вопрос | `/reset` очищает контекст |
| Вопрос про расчёт A/B/C/D из дня 26 | Полноценный ответ локальной модели |
| Backend остановлен | Видимая ошибка вместо cloud fallback/зависания |
| Длинная история | Управляемый token budget, нет скрытого превышения context |

Данные тестов и ответы сохраняем в `results/cli_dialogues.jsonl`.
Независимый субагент запускает CLI по README и проверяет фактические ответы.
Transport Telegram дополнительно проверяем на известных входных payloads:
команды, авторизация и разбиение сообщений; это не выдаётся за живой Telegram chat.

## Приватность и границы

Генерация выполняется только на ПК. Telegram передаёт сообщения через свою
инфраструктуру; README и DEMO объясняют это. Локальная CLI-сессия не использует
Telegram и не требует его токена. Cloud model credentials в этой версии не нужны.
Не добавляем инструменты, задачи по расписанию и другие функции до выполнения
обязательных измерений и сетевых проверок последующих дней.
